01  ·  Motivation & Pipeline

Why an Agent, Not Just an Optimiser

A Pyomo LP can schedule the battery · it cannot explain the schedule to an operator

The gap

  • Three misaligned signals: evening-peaking demand, midday-peaking PV, and a volatile spot price
  • The optimiser can schedule around them · but not justify an unexpected decision, e.g. charging when price isn't low, because a high-demand period is coming
  • The agent sits beside the optimiser, translating a question into a tool call and a tool's output back into a sentence

Latency tiers

1
Advisory (seconds) · reads the already-solved schedule, nothing recomputed per query
2
Re-optimise (async) · a large forecast revision or what-if triggers a background solve; the agent answers with the last valid schedule and a staleness note meanwhile

02  ·  Inputs & Price Model

Data & Forecasting

Synthetic load and PV, real DK1 spot price · LightGBM, one model per lead time

Community load

Pload(t) = (Pbase + Pdiurnal(t)) × Mday(t) + ε(t)
  • 5 sectors summed: office, logistics, manufacturing, EV (passenger), EV/HGV (depot)
  • Each: base level + time-of-day shape + weekend multiplier + Gaussian noise
  • Full series peaks at 933 kW

PV generation

PPV(t) = (SSRD / 3600) × 42.75
  • ERA5 irradiance (SSRD) scaled to a 50 MWp plant
  • Module 20% · system losses 10% · Nordic derating 5% → combined factor 42.75
  • Clear-sky peak ≈ 42.75 MW

Price forecast

P̂(t+k) = fk(Xt),  k ∈ {1 … 24}
  • One LightGBM model per lead time · not a recursive chain
  • Features: hour/DoW/month, price lags (t−k, t−k−24, t−168), 24 h rolling mean
  • Uncertainty: 15-bin residual bootstrap (5,000 samples) → P10/P90 that widen in volatile regimes

Real data, real horizon

  • DK1 day-ahead spot price, Energi Data Service, 2024-01-01 → 2025-09-30 (15,336 hourly rows) · the one component validated end-to-end against real held-out data
  • Load and PV are synthetic by design · the point is demonstrating agent/tool integration, not a production forecaster

05  ·  ReAct Agent & Tools

The Agent Layer

Framework-free ReAct loop · deterministic tools · any provider, including a local model

ReAct loop

Query→ Thought→ Tool call
Observation→ Response
  • The LLM emits a JSON tool call; Python executes it deterministically
  • The model only narrates the returned values · it never computes a figure itself

Three tools

  • bess_simulator · validates a charge/discharge action against 15–95% SoC bounds, flags violations
  • self_consumption_calculator · PV vs. load over a window, % consumed on-site vs. exported
  • electricity_cost_estimator · net grid cost (DKK) over a window, with a no-BESS baseline mode

Multi-provider router

No LangChain/LlamaIndex · provider picked from whichever API key is present:

OpenAI Anthropic Gemini DeepSeek Ollama (local) Mock (offline)

Same response contract everywhere: a price figure must carry an explicit P10–P90 range and cite the schedule source, or it counts as incomplete.

Two required queries, run end to end

"Should we charge or discharge in the next 2 hours given current conditions?"
→ calls bess_simulator: "Discharge at 750 kW, SoC 50% → 15%. Price ≈ 0.4 DKK/kWh, range 0.1–0.64 (P10–P90). Per the day-ahead LP solve."
"What was our self-consumption rate yesterday, and how could it improve?"
→ calls self_consumption_calculator: reports the rate, recommends shifting charging into the midday PV surplus, cites the schedule source.
